用 Claude 中转做 Agent 开发：多模型编排与省钱经验

KingFlow · 国内直连 AI API 中转

写这篇之前，我已经用 Claude 系列模型断断续续做了大半年的 Agent 开发。从最早一个跑 ReAct 循环的小工具，到后来带十几个工具、多层子任务的编排系统，中间踩的坑基本都跟"钱"和"稳定性"有关。这篇不讲玄乎的架构图，就聊我这一路是怎么把 token 账单压下来、把线上跑崩的概率降下去的，其中很关键的一环，是把模型调用统一走了中转。

一、Agent 开发为什么这么烧 token

刚上手做 Agent 的人经常低估它的开销。你写一个普通的聊天应用，一问一答，token 是线性的。但 Agent 不是。

第一是多轮循环。一个 Agent 完成任务往往要在"思考—调用工具—观察结果—再思考"里转好几圈。我做过统计，稍微复杂点的任务，模型来回被调用七八次是常态，复杂的能到几十次。每一轮都要把之前所有的上下文重新喂进去。

第二是工具调用的返回值。你让 Agent 读一个文件、查一次数据库、抓一个网页，返回的内容动不动几千 token，这些全都要塞回对话历史里，作为下一轮的输入。上下文像滚雪球一样越滚越大。

第三是长上下文本身。系统提示词、工具定义（JSON schema）、few-shot 示例，这些每一轮都要重复发送。我早期一个 Agent 光工具定义就占了三千多 token，跑一次任务十几轮，光这部分就重复计费十几次。

结论很直白：Agent 的 token 消耗是输入远大于输出。真正生成的答案可能就几百 token，但为了生成它，喂进去的输入是它的几十倍。想省钱，重点从来不在输出，而在怎么把这些重复的、庞大的输入成本压下来。

二、中转让多模型编排简单太多

我现在的 Agent 不是单模型跑到底，而是分工。这套分工思路，是用中转之后才真正落地的。

核心痛点是：如果直连官方，你想同时用 Claude 和别家的模型，得维护好几套账号、好几个 Key、好几个 Base URL，鉴权方式还各不一样。光是配置管理就够烦的。而走中转之后，一个 Key 就能切多个模型，改一下 model 参数就换引擎，不用碰鉴权那一层。

我现在的典型分工是这样：

  • 规划层用 claude-opus-4-8。任务拆解、决定调用哪些工具、判断子任务是否完成——这些需要强推理的环节交给旗舰模型，它想得清楚，返工少。
  • 子步骤用 claude-haiku-4-5。一旦规划层把任务切成了明确的小步，比如"把这段文本按格式抽取字段""判断这个结果算不算成功"，这类活儿根本用不上旗舰模型，交给高频低成本的 haiku 又快又便宜。
  • 部分批量、对成本敏感的环节用国产模型降本。像大批量的文本预处理、粗筛，我会路由到 deepseek-v4 或者 glm-5.1-flash 这类，跑量的时候成本差异很明显。

这套"贵模型管大脑、便宜模型管手脚"的编排，在直连时代做起来很别扭，因为切换成本太高。走 KingFlow 之后就是改个 model 字段的事。配置层面基本是这样：

import anthropic

client = anthropic.Anthropic(
    api_key="你的 KingFlow Key",   # ANTHROPIC_AUTH_TOKEN
    base_url="https://www.kingflow.ai",  # ANTHROPIC_BASE_URL
)

# 规划层：强推理
plan = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=2048,
    messages=[{"role": "user", "content": "拆解这个任务……"}],
)

# 子步骤：高频低成本
step = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "抽取以下字段……"}],
)

同一个 client、同一个 Key，两个模型跑起来。如果要路由到 OpenAI 兼容那侧（gpt-5.5 之类）或者国产模型，把请求改走 https://www.kingflow.ai/v1 那套 OpenAI 协议就行，Key 还是那一个。

三、Function Calling 走中转的实战要点

Agent 的灵魂是工具调用，这块走中转要注意几个点，都是我实际调出来的经验。

第一，选真正走官方协议的中转。 工具调用这套东西，Anthropic 的 /v1/messages 里 tools、tool_use、tool_result 的结构是有讲究的。我之前用过一家逆向类的中转，官方一更新协议，工具调用的返回格式就对不上，Agent 直接卡死。后来换到走官方 /v1/messages 协议的中转就稳多了，官方更新不容易挂——这也是我后面固定用 KingFlow 的一个原因，它是官方协议透传而不是逆向反代。

第二，工具定义照常传，不用改结构。 走中转之后 tools 参数的写法跟直连完全一样，tool_use 的 block 也原样返回。这点很重要，意味着你现有的 Agent 代码几乎零改动，就把 Base URL 换一行的事。

第三，工具返回值要控制体积。 这跟中转没直接关系，但结合前面 token 的账来看很关键：工具返回的大段结果塞回上下文之前，能截断就截断、能摘要就摘要。我一般会在工具层做一次"结果压缩"，把几千 token 的原始返回压到几百，再交回给模型。省下来的是每一轮都乘上去的。

第四，流式输出别丢。 Agent 的工具调用配合流式（stream）能更早拿到 tool_use 信号，提前去准备工具执行。中转这边流式是完整支持的，接法跟官方一致。

四、Prompt Cache 对 Agent 省钱的意义

这一块是我觉得对 Agent 最"对症"的一个点，值得单独说。

前面讲过，Agent 的开销大头是重复的、庞大的输入：系统提示、工具定义、越滚越大的对话历史，每一轮都要重发。Prompt Cache 干的就是把这些稳定不变的前缀缓存住，后续轮次命中缓存的部分，成本能砍掉一大截。

对 Agent 来说这简直是量身定做，因为 Agent 的对话前缀恰好高度稳定——系统提示和工具定义几乎每轮都一样。我这边实测，带上 cache_control 之后，连续几轮里命中缓存的输入部分，费用能下来一大截，具体幅度看任务形态，一般来说输入占比越重省得越狠。

要注意的是，得选真正透传 Prompt Cache 的中转。判断方法很土但有效：带 cache_control 连发两次同样的前缀，看第二次返回的 usage 里 cache_read_input_tokens 是不是非零。是非零，说明缓存真透传了；一直是零，那这家的缓存就是摆设。我在 KingFlow 上验过是能读到缓存命中的，所以这套省钱逻辑对我是成立的。这里我不把省了百分之多少写死，因为跟你 Agent 的上下文结构强相关，建议自己按上面的方法测一遍，以你后台的用量明细为准。

五、稳定性：重试与降级，生产别搞单点

省钱是一方面，Agent 跑在生产上，稳定性是另一条命。Agent 最怕的就是链条中某一环调用失败，整个任务前功尽弃——而它前面可能已经烧了几十轮的 token。

我的几条经验：

别单点依赖一个模型或一个通道。 我会给关键环节配降级路径：旗舰模型这次超时或限流，自动降到均衡的 claude-sonnet-4-6 再试；再不行切到别的兼容模型兜底。走中转的好处是这套降级就是改 model 参数，一个 Key 全覆盖，不用为了兜底再去接第二家的账号体系。

重试要带退避，别硬撞。 遇到 429/限流，指数退避重试比死循环强太多。Agent 的循环里我一般对单次模型调用包一层重试，最多三次，间隔递增。

幂等和断点。 长任务我会把每一步的中间结果落盘，某一环挂了能从断点续，而不是整个任务从头再烧一遍 token。这是被账单教育出来的习惯。

关注首字延迟和并发成功率。 Agent 多轮串行，每一轮的 TTFT 都会累加，首字慢的通道用户体感很差。我选中转会看国内直连的延迟表现，KingFlow 这边国内节点 TTFT 通常一两秒到三秒，比我早年自己挂代理连美国节点动不动几十秒强太多，多轮叠加下来差距非常明显。并发上来的时候，成功率和限流表现也要提前压测，别等线上高峰才发现扛不住。

六、FAQ

Q1：现有的 Agent 代码改动大吗？ 基本不大。用官方协议的中转，你只要改 Base URL 和 Key 这两行，tools、tool_use、流式这些写法全都照旧。我自己迁的时候，核心就动了配置那几行。

Q2：多模型编排会不会因为走中转就掉包，拿小模型冒充大模型？ 这取决于中转是否正规。我的做法是选用量明细透明、能在后台对账的中转，model 传什么就跑什么，后台调用日志能核。真担心的话，用同一个明确 prompt 分别打 opus 和 haiku，对比输出质量和 token 用量差异，一测就知道有没有被降级。

Q3：Prompt Cache 到底能省多少，能给个准数吗？ 给不了准数，因为它跟你 Agent 的上下文结构强相关——前缀越稳定、输入占比越重，省得越多。方法我在正文给了：带 cache_control 连发两次看 cache_read_input_tokens 是否非零，然后拿你自己的真实任务跑一轮，以后台用量为准。

Q4：为什么不直接连官方，非要走中转？ 我早年直连踩过不少坑：美区支付被拒、国内 IP 受限、自己挂代理高频长连接容易被识别掉线。做 Agent 这种高频多轮的场景，掉线一次就是一整个任务白跑。走国内直连的中转把这些底层不确定性抹平了，我能把精力放在编排逻辑本身，而不是天天跟网络和账号风控斗智斗勇。
